# 추가 개발 마감 범위: 세 가지

새 기능은 업데이트 이어받기, 경기 보호 종료, 공간 효과음 차폐로 한정한다. 다른 제안은 구현하지 않는다.

## 1. 업데이트 다운로드 이어받기

- 기존 변경 파일/4MiB 블록 증분 업데이트를 유지한다.
- 런처의 **다운로드 중단**을 누르거나 다운로드 중 창을 닫아도 기존 설치본은 건드리지 않는다. 다시 실행해 **업데이트 및 실행**을 누르면 같은 서버·릴리스 URL·파일 해시의 캐시를 재검증하고 재사용한다.
- 캐시는 설치 폴더의 `.update-cache`에 보관한다. 검증된 블록은 다시 받지 않고 중단된 블록/구형 전체 파일의 남은 바이트는 HTTP Range로 요청한다.
- 크기·Content-Range·블록 SHA-256·최종 파일 SHA-256을 확인한다. 다른 릴리스의 조각은 섞지 않는다. 손상된 블록은 폐기하고 다시 받는다.
- Range 미지원 서버라면 해당 파일을 전체 다운로드로 전환한다. 이어받기를 무조건 지원하는 것처럼 잘못된 바이트를 붙이지 않는다.
- 업데이트 목록 응답 제한은 기존 5초, 다운로드 헤더/각 읽기의 무응답 제한은 15초다. 오류 뒤 받은 캐시는 유지하고 자동 무한 재시도하지 않는다.
- 모든 파일 검증이 끝난 뒤 교체한다. 적용 중에는 중단 버튼을 비활성화한다. 파일 잠금 등으로 적용에 실패하면 이미 교체한 파일도 롤백하고, 캐시는 다음 시도에 재사용한다.
- 성공적으로 적용한 파일의 캐시만 정리한다. 실패/중단된 다운로드의 `.update-cache`를 삭제하면 이어받기는 초기화되지만 기존 설치본과 저장 데이터는 영향을 받지 않는다. 실행 중인 런처의 작업 폴더를 수동 삭제하지 않는다.
- 단일 파일 런처: `Saved/FinalThree/LauncherPublish/ProjectProject01ClientLauncher.exe`. 기존 런처를 종료한 다음 게임 실행 파일이 있는 **클라이언트 Windows 폴더 안의 기존 런처**와 교체한다. 이 새 런처는 사용자에게 한 번 전달해야 한다. 게임 업데이트만으로 기존 런처 자체가 교체되지는 않는다.

검사: 중단 후 블록/바이트 재개, 캐시 손상, 릴리스 분리, 전체 파일 fallback, 잘못된 응답/해시 차단, 실제 로컬 Kestrel HTTP 206, Windows 파일 잠금 후 롤백 및 캐시 재적용. 운영 서버가 아닌 격리 파일과 로컬 테스트 HTTP를 사용한다.

## 2. 진행 중인 경기를 보호하는 운영 중지

도우미의 **경기 종료 후 운영 중지**:

1. 신규 게임 시작을 차단한다. 클라이언트의 기존 서버 운영 상태 갱신 경로로 시작 버튼이 비활성화된다.
2. 아직 실제 시작하지 않은 카운트다운/자리 대기/서버 준비는 취소하고 기존 방과 로그인을 유지한다.
3. `Started` 경기는 유지한다. 입장 허가, heartbeat, 경기 진행과 기존 결과/복귀 처리는 계속 허용한다.
4. 모든 경기에서 전원 복귀/이탈 정리가 완료되어 세션이 비면 경기 프로세스를 정상 정리하고 **게임 서버 운영만 중지**한다. 백엔드와 MySQL 및 기존 대기방은 유지한다.

**종료 대기 취소**는 완료 전에 신규 시작을 다시 허용한다. 이미 운영 중지가 완료됐다면 취소로 임의 재시작하지 않고 **게임 서버 운영 시작**을 사용해야 한다. 기존 즉시 중지는 **게임 서버 운영 즉시 중지**로 명확히 구분했다.

도우미는 종료 대기 동안 남은 세션 수를 표시한다. 이 도우미가 실행한 백엔드를 중지하거나 창을 닫을 때 활성 세션이 확인되면 경기 중단 경고를 표시한다. 경기를 보호하려면 창을 열어 두고 종료 완료를 기다린다. 상태 확인에 실패했을 때도 확인 없이 안전 종료됐다고 표시하지 않는다. backend drain은 운영 프로세스의 메모리 상태이며, 백엔드 자체가 비정상 종료되거나 강제로 종료되는 상황을 보호하는 기능은 아니다.

이미 결과 화면에 있더라도 아직 돌아오지 않은 사용자가 있으면 기존 세션 수명 규칙에 따라 기다린다. 즉시 중지/작업 관리자 강제 종료는 경기 보호 대상이 아니다. 수동 실행한 임의의 다른 서버 프로세스를 자동 관리하는 기능도 아니다.

검사: 관리자 인증, 새 시작 거부, 대기열 취소, 기존 경기 입장 티켓/heartbeat 유지, 한 명 복귀 시 유지, 전원 복귀 후 종료, 종료 대기 취소, 중지 완료 뒤 늦은 실행 방지. 실제 API와 별도 MySQL 23307을 사용하며 UE 프로세스는 모의 객체다.

## 3. 벽·문에 따른 공간 효과음 차폐

- 싱글/멀티의 플레이어·파트너·마네킹 발소리 및 급정지 합성음, 플레이어 신음/비명, 쓰러지는 소리에 적용한다.
- 따로 지정한 발소리 음원도 transient attenuation 사본을 사용한다. 원본 Sound Attenuation 에셋을 변경하지 않고 런타임에 30m까지 거리 배율 1, 30~60m 선형 감쇄, 60m에서 0을 적용한다. 원본의 오래된 거리 설정과 Blueprint override가 이 정책을 무시하지 않도록 공통 적용한다.
- 차폐는 소리와 청취자 사이를 `Visibility` 복합 충돌(메시 표면)로 검사한다. 일체형 맵의 볼록 단순 충돌이 방 내부의 빈 공간까지 채워 차폐하던 오판을 피한다. 같은 방 안에서 사이에 장애물이 없으면 추가 차폐를 하지 않고, 서로 다른 밀폐 공간의 벽/닫힌 문 또는 층 사이 바닥이 실제로 선을 가로막을 때만 음량 배율 0.25, 저역 통과 필터 600Hz, 전환 0.15초를 적용한다. 거리 감쇄와 차폐는 별도로 계산한다.
- 벽과 닫힌 문은 Query Collision이 있고 Visibility를 Block해야 한다. 열린 문이 여전히 가상의 닫힌 충돌체를 남기면 계속 차폐되는 것이 정상이다. 문을 열 때 충돌체도 실제 위치/상태와 맞춰야 한다.
- 마네킹 발밑 검사도 복합 충돌을 사용하고, 발소리 발생점을 실제 바닥 표면의 바깥쪽으로 조금 띄운다. 충돌 메시가 없는 시각적 벽은 차폐되지 않는다. 메시가 `Use Simple Collision As Complex`로 설정되어 있으면 복합 검사도 거친 단순 충돌을 사용하므로, 일체형 맵은 `Simple And Complex` 또는 적절한 `Use Complex Collision As Simple` 설정과 실제 삼각형 충돌이 필요하다. 음향을 위해 모든 Visibility를 Ignore로 바꾸면 안 된다.
- 플레이어 자신의 심장박동, 마네킹 포획 성공 확인음, UI/배경음악은 이 월드 차폐에 포함하지 않는다. EOS 음성의 생존자 전용 채널/역할/거리 규칙은 변경하지 않는다. 음성에 벽 필터를 추가한 것이 아니다.
- AI 감지·추적·시야 정지·공격 판정은 변경하지 않는다. 순수하게 청취 측 공간 효과음 처리다.

자동 검사는 차폐 설정, 원본 에셋 비변경, 30~60m 거리 배율, 벽 충돌/해제 및 기존 UI 회귀를 확인한다. 헤드리스/무음 검사이므로 실제 청감과 완성된 맵의 문 충돌까지 검증한 것은 아니다. 실제 재생 차폐 배율/필터를 에디터에서 확인하는 기본 엔진 명령은 `Docs/AudioOcclusionAndPartnerContact.md`에 설명한다.

## 반영 및 마지막 확인

- 도우미/백엔드: 최신 빌드를 재실행한다. 실행 중인 운영 프로세스는 이번 작업에서 임의로 중지하거나 재시작하지 않았다.
- 런처: 위의 새 런처를 기존 Windows 패키지 폴더에 교체해서 배포한다. 단독 폴더에서 실행하면 게임 실행 파일이 없으므로 게임을 찾을 수 없다.
- 게임: 차폐는 새로운 클라이언트 패키징 후 반영된다. 실제 경기 서버는 이전에 구현한 세션 관리/티켓 규약을 포함한 최신 호환 데디 패키지를 사용한다. 이번 작업에서는 Dedicated Server 패키징이나 외부 PC 실게임을 실행하지 않았다.
- 실제 확인은 다운로드 중단/재개, 진행 경기 중 안전 종료 요청 후 전원 복귀, 같은 거리에서 벽/문 유무에 따른 소리 비교로 한정한다.

이 세 항목의 반영 이후 새 기능 추가는 종료하고 발견되는 결함 수정과 안정화만 진행한다.
