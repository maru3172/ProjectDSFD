# 사건 기록: 배틀패스 / 기본 기록(로어) 분리 — 개발 기록

## 요약

- 목표: 사건 기록을 `배틀패스`와 `기본 기록`으로 나누고, 기본 기록에서 플레이어와 그 밖의 로어 기록을 열람하게 한다.
- 핵심 문제: 로어를 둘 자리·작성 경로·해금 규칙이 없었고, 잠긴 내용이 클라이언트로 새면 안 된다.
- 해결: 서버 `case_lore`(운영자 작성, 조건별 해금, 잠긴 제목·본문 미전송), 도우미 `기본 기록 작성` 창, 게임 하위 탭과 목록·읽기 화면.
- 결과: 격리 검사 362개(기본 기록 14개 포함) 통과, 도우미 UI 검사 27개 통과, UE 사건 기록 테스트 9개 통과, 렌더 확인.
- 상태: 커밋 `d0de20f`(2026-11-04)에 포함. 실제 운영 서버 게시·실제 글 작성은 하지 않음(처음에는 비어 있음).

## 요청·목표·범위 (9-2)

- 사용자 발언: "사건 기록을 배틀패스 / 기본 기록으로 나눠서 기본 기록은 플레이어나 플레이어 외의 로어 같은 느낌의 저장된 기록들을 열람할 수 있는거로".
- 질문으로 확정한 결정(사용자 선택): 위치 = 사건 기록 안의 두 탭 / 글 = 도우미에서 직접 작성 / 해금 = 조건별.
- 제약: 사건 날짜 등 미정 사실을 지어내지 않음, 추가 설명 문구 최소화, UI 겹침 금지, 운영 DB(3307)·3306 불가침, 검사는 23307 격리 DB.
- 범위 변경: 원 세션이 다른 요청으로 넘어가면서 작업을 별도 세션으로 인계해 마무리했다(인계 계획: 검사 등록·게임 UI·빌드·문서).

## 기존 구조·흐름 (9-3)

```text
도우미 CaseLoreForm --PUT /api/admin/case-records/lore--> 백엔드 CaseLore (case_lore JSON 한 행)
게임 UProjectCaseRecords.Refresh --GET /api/case-records--> CaseRecords 스냅샷 + lore.records(계정별 해금 계산)
                                                       └─> UProjectCaseRecordWidget::BuildLore (Page "Lore")
```

- 해금 계산 입력: 계정 레벨(`CaseRecords.Level`), `case_achievements`, `case_claims`의 조사 파트 보상 키, 시즌 종료 여부.
- 기존 파트 이야기와 같은 기준: 파트 조건은 파트 보상 수령 또는 시즌 종료 시 열림.

## 문제·증상 (9-4)

- 잠긴 기록의 본문이 응답에 섞이면 클라이언트에서 볼 수 있다 → 서버가 잠긴 항목의 제목·본문을 빈 문자열로 보낸다.
- 작성 창 버그(작업 중 발견): 기록을 추가하고 본문을 입력하면 프로세스가 스택 오버플로(종료 코드 -1073741571)로 죽었다. 재현: 도우미 UI 검사 `--case-ui-checks`.
- 다른 세션 변경으로 인한 빌드 실패: 마지막 재빌드 때 `MiniGames.cs`의 `Stars` 인자 오류(CS1501). 당시 다른 작업이 그 파일을 수정 중이었다.

## 판단·결정 (9-5)

- 저장 형식: 카탈로그처럼 JSON 한 행으로 통째 교체. 항목별 행보다 단순하고, 순서 = 목록 순서를 그대로 보존.
- 업적 이름은 서버가 아니라 클라이언트(`ProjectCaseProfile::Achievement`)가 조건 문구로 만든다. 이름 사전이 클라이언트에만 있기 때문.
- 조회 실패 시 게시 버튼을 끈다. 빈 목록으로 기존 글을 덮어쓰는 사고를 막기 위함(파트 스토리 창과 같은 방식).
- 스택 오버플로 원인: `list.Items[i]=...`가 `SelectedIndexChanged`를 다시 일으켜 `Capture()`가 무한 재귀. 해결: 갱신 중 플래그로 재진입 차단 + 제목이 같으면 갱신 생략.
- `MiniGames.cs` 오류는 다른 작업의 진행 중 편집으로 판단해 손대지 않았다(그 작업이 끝난 뒤 빌드 성공 확인).
