# 경량 진단과 서킷 브레이커

## 사용 순서

1. 수정된 서버 도우미와 백엔드를 다시 실행한다. 도우미의 **서버 실행·운영 → 진단 대시보드 열기**를 누른다. 이 버튼은 대시보드 도구만 증분 빌드한 뒤 연다. 게임 패키징·업데이트 게시는 실행하지 않는다.
2. 게임 진단은 기존 에디터 **Tools → ProjectProject01 Diagnostics**에서 캡처를 시작/종료하고, 대시보드에서 `Saved/Diagnostics`를 연다.
3. 백엔드 진단은 **백엔드·풀 진단** 탭에서 백엔드 주소와 기존 운영자 API 키를 입력한 뒤 **수집 시작**을 누른다. 키는 저장하거나 명령줄 인자로 전달하지 않는다. 기본 수집은 꺼져 있다. 서버 설정 `Diagnostics:Enabled=true` 또는 환경변수 `Diagnostics__Enabled=true`로 시작 시 수집을 선택할 수도 있다.
4. **수집 중지**는 백엔드 표본 생성·파일 기록을 멈춘다. 대시보드를 닫는 것만으로 서버의 수집을 중지하지는 않는다. **기록 열기**로 `Saved/Diagnostics/BackendMetrics/backend-metrics-*.jsonl`을 최대 8개 선택해 오프라인으로 볼 수 있다. 순환 보관되므로 보존할 비교 자료는 별도 폴더로 복사하거나 CSV로 내보낸다.

진단 API는 `/api/admin/diagnostics` GET과 POST(`?enabled=true/false`)이며 기존 `X-ProjectProject01-Admin-Key` 인증을 사용한다. 공개 인터넷에서 평문 HTTP로 운영자 키를 전송하지 않는다. 대시보드는 공개 HTTP 주소와 자동 리다이렉트를 거부하며 인증 실패/연결 실패 시 자동 조회를 중지한다. 요청 전체(헤더·본문 수신 포함)는 5초로 제한한다.

이것들은 서로 다른 범위다. HTTP 요청 처리량은 DB 트랜잭션 TPS가 아니며, OS 핸들 수는 파일 디스크립터 수가 아니다. TCP/UDP 엔드포인트 수도 정확한 소켓 핸들 수로 부르지 않는다. 비동기 요청 수와 스레드 수는 일대일이 아니다.

### 실제 서킷 브레이커 규칙

- 일시적 실패(연결 실패·타임아웃·HTTP 408/429/5xx)가 **3회 연속**이면 **10초** 동안 새 요청을 차단한다.
- 이후 새 요청이 들어오면 **단 1건**만 복구 시험(HalfOpen)을 허용한다. 나머지는 기다리라는 안내를 받는다. 복구 시험이 성공하거나 서버가 일반적인 4xx 응답을 주면 정상(Closed)으로 돌아간다. 비밀번호 오류/권한 거부 같은 4xx는 서버 장애에 누적하지 않는다.
- 복구 시험도 실패하면 다시 10초 차단한다. 취소되거나 완료 통지가 사라진 복구 시험도 무한 대기하지 않는다. 요청 제한 시간+1초 뒤의 다음 요청은 다시 차단 구간으로 들어간다.
- 이전 상태/이전 접속 주소에서 늦게 도착한 응답은 새 상태를 임의로 해제하지 못한다. 클라이언트에서 백엔드 주소를 바꾸면 그 인스턴스의 보호 상태를 초기화한다. 로그인 계정이나 다른 PC로 상태를 전파하지 않는다.
- 차단 중에도 로컬 로그아웃은 가능하다. 기존 자동 재시도 횟수를 늘리지 않으며 새 쓰기 요청 재전송 기능을 추가하지 않는다. 결과 복구가 차단되어도 보류 파일은 보존하고, 기존 성공 처리 절차에서만 완료된 파일을 정리한다.
- 보호 대상은 위 표의 지정 경로다. 상태 확인·음성 SDK·모든 DB SQL 명령까지 전역 차단하는 기능은 아니다. 실제 SQL 실행 실패를 연결 획득 실패와 혼동하지 않는다.

### 해석 제한

- GC 전후 순변화는 동시 할당·할당자 재사용을 포함한다. 프로세스 RAM이 그대로라고 GC가 아무것도 정리하지 않은 것은 아니다. Unreal 시작~완료 경과 시간은 정확한 stop-the-world 시간이나 스레드 CPU 합계가 아니다. CLR Gen0 수집 횟수에는 상위 세대 수집도 포함되므로 세대별 횟수를 합산하지 않는다.
- Unreal의 전체 C++ malloc 바이트 할당률, CPU 하드웨어 캐시 히트/미스, OS 대기/파일 캐시, GPU 드라이버 캐시, Windows 열린 파일 디스크립터 목록은 경량 모드에서 후킹/열거하지 않는다. 해당 항목은 측정 불가로 표시한다. 필요하면 별도의 짧은 정밀 추적을 사용한다.
- 지원되지 않는 할당자/구형 캡처는 0으로 채우지 않는다. 현재 기본 Windows 에디터의 Mimalloc은 Binned의 해당 사용/OS 보유 카운터를 제공하지 않는다. 진단 때문에 게임 할당자를 교체하지 않는다.
- 캐시 히트/미스는 음성 참가자 명단 캐시에 한정된다. 조회 시간은 락 획득 이후 사전 조회만 측정하며 락 대기/명단 전체 응답 생성 시간을 포함하지 않는다. 문자열 크기는 컨테이너·키·할당 오버헤드를 제외한 추정치다. 이 캐시는 용량 초과 시 제거 대신 등록을 거부하므로 용량 제거가 0인 것은 정상이다. TTL 만료는 별도 집계한다.
- HTTP 풀에는 호스트/프로토콜을 통틀어 단일 최대 용량이 없다. 활성/전체 열린 연결 비율을 최대 용량 사용률이라고 부르지 않는다. MySQL 풀 값은 여러 풀의 합계이므로 특정 풀 하나의 포화를 합계만으로 확정할 수 없다. 원본 풀 이름/연결 문자열은 저장하지 않는다.
- 미지원/아직 발생하지 않은 풀 계측이나 평균 표본은 비어 있는 값이다. Kestrel 대기 요청은 해당 런타임/프로토콜에서 제공하는 범위만 측정한다. 사용 중 스레드 수/비율은 CPU 사용률이 아니다.
- 같은 에디터 프로세스에 들어 있는 여러 PIE 월드는 프로세스 RAM·스레드·소켓·UObject 생성률·GC를 공유하므로 합산하지 않는다. 서킷 브레이커는 반대로 각 GameInstance의 로컬 상태다.

## 경량화 방법과 상한

- 기존 게임 표본은 1초 간격, OS 테이블 조회는 프로세스별 5초 간격 캐시를 공유한다. 캡처를 끄면 UObject 생성 리스너를 해제한다. 전역 메모리 할당 후킹이나 주기적 강제 GC/캐시 삭제를 하지 않는다.
- 게임 캡처는 최대 7,200표본 또는 50,000이벤트에서 자동 중지하고 `Inconclusive`로 처리한다. 이벤트 메시지는 최대 2,048자로 제한한다. 긴 시험은 캡처를 나눠서 보관한다.
- 백엔드는 요청마다 작은 고정 카운터만 갱신하고, 약 5초마다 표본을 만든다. 완료 수·오류 수·시간·동시 요청 수는 짧은 잠금으로 같은 시점에 복사하며 카운터 잠금 안에서 I/O·OS 조회·외부 계측 콜백을 실행하지 않는다. 풀의 up/down 기준선을 놓치지 않도록 허용된 기본 계측 리스너는 시작 시 연결한다. 상세 히스토그램·오류 기록과 파일 저장은 수집 중에만 한다. 요청 경로·쿼리·본문·헤더·계정별 태그를 축적하지 않는다.
- 새 오류 상세는 64개 조합과 초과 집계 1개로 제한한다. 대시보드 조회 자체는 HTTP 처리량/오류율에서 제외한다. 표본 수집 자체의 시간도 `Diagnostics.SampleMs`로 표시한다. 파일 쓰기와 외부 대시보드 비용은 이 수집 시간에 포함하지 않는다.
- 백엔드 기록은 도구 소유 8개 슬롯, 슬롯당 최대 120표본으로 순환한다. 다른 사용자 파일을 열거/삭제하지 않는다. 대시보드 파일 읽기는 최대 8파일·파일당 4 MiB, 행당 64 KiB, 최근 720표본으로 제한하며 슬롯 번호가 아니라 UTC 시각으로 최신 표본을 고른다.
- 그래프는 시리즈당 최대 800개의 첫/마지막·구간 최솟값/최댓값 대표점을 그린다. 원본 CSV/JSONL을 이 그래프 축약으로 수정하지 않는다. 선택된 게임 캡처는 그래프 항목을 바꿀 때 매번 다시 읽지 않는다.

상한과 카운터 설계는 비용을 제한하기 위한 것이지 어떤 PC에서도 비용이 0이라는 보증은 아니다. 실제 부하 시험에서는 진단 OFF/ON을 같은 조건에서 비교하고 기존 진단 오버헤드 탭과 백엔드 표본 수집 시간도 함께 확인한다.

## 비교·검증

### 추가 진단의 장기 추세 (2026-10-22)

대시보드 **진단 전체, 비교**에서 확인한다. 기존 성능·위험 항목을 추가 진단과 하나의 선택 목록으로 합쳤다. 이전의 두 하위 탭은 제거했고, 기존 항목의 집계 공식과 기록 형식은 유지한다. 기존 성능·위험 값은 `전체 경기` 범위, 새로운 게임 진단은 역할별 범위로 분리한다.

- **범위**: 전체 / 게임 / 백엔드. **영역**: GC·회수·기준선, 메모리, 텍스처 풀, 캐시, 프로세스·스레드·소켓, 스레드 풀, 객체·메모리 할당률, DB 연결 풀, HTTP 연결 풀, HTTP 요청·처리량·큐, 오류·타임아웃·재시도 상세, 서킷 브레이커, 진단 수집 비용·구간.
- 항목명·탭·버튼·표 머리글은 한국어로 표시한다. 원본 키를 항목명 뒤에 영어로 붙이지 않으며 CSV·JSON 내부 키와 원본 로그·식별자는 호환성을 위해 유지한다. 이번에 추가한 모든 게임 카운터, GC 전후 원본·순감소·반복 GC 후 기준선 변화, 모든 백엔드 숫자 지표, 오류 종류별 횟수와 실제 원인·HTTP 코드별 횟수/시도/상한/다음 대기 시간이 대상이다. 캐시·메모리의 정성 판정과 측정 범위 설명은 선택한 캡처 아래 근거란에 보존된다. 이 판정 자체를 임의의 성능 점수로 만들지는 않는다.
- 게임 캡처는 기존 진단 폴더를 열거나 Refresh하면 자동 집계된다. 위쪽 맵·결과·검색 필터도 게임 장기 추세에 적용된다. 게임 역할별 값은 분리하며 공유 PIE 프로세스 메모리·GC를 합산하지 않는다.
- 백엔드는 수집을 중지한 뒤 **백엔드 원본 기록 가져오기**로 `Saved/Diagnostics/BackendMetrics/backend-metrics-*.jsonl`을 선택한다. 서로 다른 시험은 보관한 원본도 함께 가져온다. 라이브 화면의 최근 720표본만 가져오는 것이 아니라 선택한 원본 전체를 집계하므로 현재 순환 슬롯의 최대 960표본도 포함한다. 원본 수집에는 기존처럼 운영자 인증이 필요하며 오프라인 비교에는 키를 저장하지 않는다.
- 시간순 캡처 번호가 가로축이며 아래 표에서 시작·종료 시각, 역할/프로세스, 전체·유효 표본 수, 조건, 값을 확인한다. 백엔드는 CaptureId와 PID로 분리하며 게임 TestRunId와 임의로 짝짓지 않는다. 서로 다른 머신·빌드·맵·부하의 기록은 조건을 직접 맞춰 비교한다.
- **권장 집계 / 평균 / 최대 / 최소 / 마지막 / 합계·관측 증가량**을 선택한다. 원시 구간 발생 횟수는 합계, 누적 카운터는 첫 관측 이후의 증가량(리셋 감지), 서킷 상태는 마지막 값이 권장이다. 누적 카운터가 한 번만 관측됐다면 증가량은 측정 불가다. 상태는 평균·합계로 계산하지 않는다. GC 빈도·요청 처리량 같은 사전 계산 단일 요약은 **권장 집계**에서 본다.
- 평균은 유효 관측 시간으로 가중한다. HTTP 서버 오류율·4xx 비율·평균 요청 시간은 완료 요청 수로 가중한다. 원본 캐시 히트/미스 비율·조회 시간은 프로세스 수명 누적값이므로 권장 집계는 마지막 값이다. 풀 대기 시간은 원본 구간 평균의 시간 가중값이며 전체 요청별 정확한 평균이라고 부르지 않는다. GC 전후 순감소는 음수(증가)도 보존한다.
- **비교 요약 저장**으로 `.diagnostic-history.json`을 저장하고, 이후 **비교 요약 열기**로 이전 시험과 함께 비교한다. 앱을 닫아도 보존하려면 저장해야 한다. 원본은 수정하지 않는다. 같은 캡처 ID를 다시 가져오면 중복 합산하지 않고 해당 구간 요약을 교체한다. 다른 일부 구간만 다시 가져온 경우 이전 전체와 자동 합치지 않으므로 보관한 원본을 함께 선택하고 표본 수를 확인한다.
- 백엔드 순환 파일은 오래된 표본을 덮어쓴다. 요약이나 원본을 미리 보관하지 않았다면 이미 덮어쓴 과거 값은 복원할 수 없다. 미지원 할당자·Windows 파일 디스크립터·구형 기록의 누락값은 **측정 불가**이며 정상 0으로 대체하지 않는다. 빠진 캡처는 그래프 선도 끊어서 표시한다.
- 경량 상한: 가져오기 한 번에 원본 64파일·파일당 4 MiB·행당 64 KiB·최대 8,192표본. 장기 요약은 역할별 최대 2,048캡처·캡처당 최대 1,024지표·파일 최대 32 MiB다. 상한을 넘으면 안내하고 해당 가져오기를 반영하지 않는다. 조용히 일부 항목을 삭제하지 않는다. 차트는 기존 시리즈당 800대표점 상한을 유지한다. 요약 계산은 외부 도구에서만 수행하며 게임 표본 빈도를 늘리지 않는다.
