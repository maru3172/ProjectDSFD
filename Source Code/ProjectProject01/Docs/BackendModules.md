## 모듈 연결 방식

`Platform/BackendModules.cs`의 `IBackendModule`이 플랫폼과 게임 사이의 유일한 약속입니다. 플랫폼은 정해진 시점마다 등록된 모듈을 순서대로 부르고, 게임 기능의 이름은 모릅니다.

| 시점 | 메서드 | 이 게임에서 하는 일 |
| --- | --- | --- |
| 서버 시작 | `EnsureSchemaAsync` | 각 모듈의 표 만들기(플랫폼 표 다음) |
| API 등록 | `MapRoutes` | 봇전, 사용자 지정 규칙, 어픽스, 사건 기록 API |
| 경기 시작 기록 | `OnMatchStartedAsync` | 봇 로스터 고정, 규칙·어픽스 고정, 봇 레이팅 기준, 사건 기록 모드·조사 |
| 접속 티켓 확인 | `AddTicketFieldsAsync` | 응답에 `bots`, `customRules`, `affixes` 추가 |


### 등록 순서 (바꾸면 안 되는 이유)

`BotMatch → CustomRules → Affix → BotRating → CaseRecords → MainQuest`. 봇 레이팅은 사용자 지정 규칙과 어픽스가 기록된 뒤에 "공식 경기인가"를 판단하므로 그 뒤에 와야 합니다. 이전 코드의 실행 순서와 같습니다.

## 다른 게임에서 쓰려면

1. `Platform/`과 `Program.cs`를 가져옵니다.
2. `Game/` 대신 자기 게임의 모듈을 `IBackendModule`로 만들고 `GameModules.All`에 넣습니다.
3. 지금은 아직 2단계 전이라, 아래 목록의 플랫폼 코드가 이 게임 기능을 직접 부르므로 그대로는 컴파일되지 않습니다.

## 결정 (2026-11-01)

2단계(아래 결합을 없애고 프로젝트를 둘로 나누기)는 하지 않습니다. 다음 프로젝트가 같은 형태(언리얼, 소수 인원 세션)일지 정해지지 않았고, 방·매칭 핵심 코드를 바꾸는 위험에 비해 이 게임에는 얻는 것이 없기 때문입니다. 대신 새로 만드는 게임 기능은 `Game/`에 `IBackendModule`로 넣어 결합을 늘리지 않습니다. 같은 형태의 다음 프로젝트가 정해지면 그때 아래 목록부터 진행합니다.

## 남은 결합 (2단계에서 연결점으로 바꿀 것)

플랫폼 코드가 게임 코드를 직접 부르는 곳은 약 38곳입니다.

| 파일 | 부르는 것 | 바꿀 방향 |
| --- | --- | --- |
| `Platform/LobbyEndpoints.cs` (~21) | 봇 방 여부, 봇 포함 정원·역할 배정, 방 상태의 봇·규칙·어픽스, 경기 결과 뒤 사건 기록·메인 퀘스트·봇 경험·레이팅, 기권, 사용자 지정 경기 비공식 처리 | 방 구성원 공급자(사람 + 봇), 역할 배정 규칙, 방 상태 추가 필드, 결과 확정 후 연결점, "비공식 경기" 판정 연결점 |
| `Platform/RandomMatchmaking.cs` (6) | 봇 레이팅으로 매칭, 역할 선택 | 매칭 점수 공급자, 역할 규칙 |
| `Platform/GameServerDemandManager.cs` (3) | 봇 포함 정원 확인, 역할 배정 | 위와 같은 방 구성·역할 연결점 |
| `Platform/OpenParties.cs` (3), `Platform/SocialProfiles.cs` (3), `Platform/OpenMatchObservers.cs` (2) | 역할 선택, 사건 기록 계정 잠금·프로필, 봇 방 확인 | 계정 프로필 추가 필드, 방 구성원 공급자 |

이 결합이 0이 되면 `Platform`을 별도 프로젝트(클래스 라이브러리)로, `Game`을 그 위의 프로젝트로 나눕니다. 역할 이름(마네킹·생존자)과 정원(3명)이 방·매칭 코드 깊이 들어 있어, 2단계는 단순 이동이 아니라 방 구성과 역할 규칙의 설계 변경입니다.
