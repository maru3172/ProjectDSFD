## 확인한 검사

- Unreal에서 100ms 지연·2% 패킷 손실 세 클라이언트, 싱글 타이틀 복귀, 설정, 셔터, 엘리베이터를 검사했다. 6개 실패 0건이며 싱글 복귀와 세 클라이언트 검사에 경고가 있었다.
- 경기 맵 3개의 역할별 스폰과 설정된 이동 목적지, 엘리베이터·셔터 배치를 검사했다. 프롤로그 전체 진행도 통과했다.
- 격리 MySQL에서 이벤트 공개 시간, 운영자 권한, 중복 예약·동시 지급·회수, 버그 제보를 확인했다. SQL 백업, 한글 복원, 해시 검증, 실패한 복원의 롤백도 통과했다.
- Unreal Editor, 백엔드, 서버 도우미, 런처, 진단 대시보드의 개발 빌드가 통과했다. 패키징 설정 검사 32개와 진단 대시보드 자체 검사도 통과했다.

## 남은 검증과 제한

1. 새 Win64 클라이언트·데디케이티드 서버·런처를 패키징한 뒤 실제 로그인 → 경기 → 층 이동 → 결과 → 로비를 검수한다. 이번 작업에서 운영 환경에 게시하거나 운영 DB를 복원하지 않았다.
2. 패키지의 안전 실행·그래픽 복구, 실제 PC 벤치마크, 포토 모드의 PNG 저장, 장면 3개의 개별 다시보기를 확인한다.
3. 실제 Win64 덤프와 같은 빌드의 PDB를 준비해 CDB 스택·줄 번호·원인 묶음을 검증한다. 이 PC의 표준 Windows SDK 경로에서는 CDB를 찾지 못했다.
4. 실제 경기를 수집해 운영 분석의 집계 수와 종료 결과를 대조한다. 튜토리얼의 ‘이후 기록 없음’은 마지막 기록으로 추정한 값이며 실제 종료 원인을 단정하지 않는다.
5. 공개 범위의 A/B는 계정별 고정 분할이다. 범용 실험 지표 분석과 대화 그래프에서 연결 자체를 바꾸는 기능은 포함되지 않았다. QA의 문자열 검사는 등록 여부를 확인하며 각 해상도에서 실제로 잘리는지는 화면 검수가 필요하다.

## 사용 위치

- 서버 운영의 **진단·운영**에서 장애 알림, 플레이 분석, 운영 변경 이력, 공개 범위, 예약 지급, Win64 덤프 분석을 연다.
- 서버 운영의 **콘텐츠·소통**에서 이벤트 게시물의 공개 시간을 정하고 메인 퀘스트·대화 흐름을 편집한다.
- 서버 도우미의 **DB 백업·복원**에서 외부 ZIP 저장·가져오기와 격리 복원 시험을 실행한다.
- 백엔드 설정의 `Administrator:Operators:<이름>:Role`에 `Observer`, `Support`, `Content`, `Service` 중 하나를 두고 같은 항목의 `ApiKey`에 개인 키를 넣는다. 운영 도우미 상단의 운영자 키 입력란은 이 값을 사용한다.
- 플레이어는 싱글 저장소의 **프롤로그 · 장면 다시보기**, 일시정지의 **포토 모드**, 환경설정 그래픽의 **PC 성능 측정**, 경기 메뉴의 **버그 제보**에서 새 기능을 사용한다.
