# 보이스 네 가지 개선 및 기존 기능 점검 (2026-10-16)

이 문서는 1차 작업 당시의 기록이다. 아래에서 후속 보완으로 분류했던 **1~5번은 이후 구현했다.** 현재 동작·보관 정책·새 추가 점검 결과와 배포 조건은 [후속 구현 및 전체 게임 점검](VoiceSecurityAndWholeGameReview.md)을 기준으로 확인한다. 후속 작업에는 RPC와 프로토콜 버전 변경이 포함된다.

## 구현한 범위

1. 세션/접속 시도마다 증가하는 세대 번호를 EOS 사용자 인증, 서비스 연결, 로그인, 토큰 HTTP, 채널 입장 완료 콜백에 전달한다. 종료/맵 이동/재시도 후 예전 세대의 응답은 현재 상태를 바꾸지 않는다. 보관한 HTTP 요청은 취소 전에 완료 델리게이트를 해제한다. 늦게 성공한 다른 채널 입장은 정리한다. SDK 초기화는 전역 공유 작업이므로 현재 초기화 대기 상태만 다음 단계로 진행시킨다.
2. 연결 단계·실패·재시도 상태를 UI에 구분한다. 단계별 응답 제한 10초, HTTP 5초, 자동 재시도 최대 3회와 2/4/8초 대기를 적용한다. 무한 연결 중 대신 최종 실패와 수동 재시도 버튼을 제공한다. 원본 토큰/비밀키는 실패 안내에 포함하지 않는다.
3. 동일 계정·MatchId의 생존자 설정은 맵 이동 중 보존한다. 이전 컨트롤러의 일반 종료와 맵 이동 중 종료를 구분하고, 재구성 때 계정·매치·역할을 재검사한다. 전환 시 PTT/상시 송신은 꺼서 의도하지 않은 송신을 방지한다. 로그인 종료/다른 경기/역할 변경에서는 이름과 개인별 수신 설정을 정리한다. 서버 컨트롤러의 seamless travel 시 검증된 표시 이름 복사도 보완했다.
4. 토큰을 발급한 계정과 EOS ID를 임시 디렉터리에 연결한다. 실제 닉네임은 현재 DB 사용자 정보에서 읽는다. `/api/voice/participants`는 로그인 계정이 해당 진행 중 경기의 생존자인지 다시 확인한 후 같은 경기의 생존자 이름만 반환한다. 마네킹/타 경기 사용자는 조회할 수 없다. 디렉터리는 매치 최대 4096개, 매치별 최대 3명, 5분 비활성 만료로 제한한다. 다른 계정이 이미 등록한 같은 음성 ID의 중복 연결은 거부한다.

이름은 15초 간격으로 갱신한다. 백엔드 재시작으로 임시 이름 연결이 없어졌다면 통화를 끊지 않고 토큰 요청으로 이름 연결만 재등록한다. 이름 갱신 실패는 이미 연결된 통화를 중단하지 않는다. 클라이언트가 제출한 닉네임은 신뢰하지 않는다. 다만 EOS ID 자체의 소유 증명은 아래 별도 보안 보완 항목이다.

## 반영과 확인

- 클라이언트는 재패키징/업데이트 게시, 백엔드는 최신 빌드로 재실행해야 한다. 서버 컨트롤러 이름 carryover 보완까지 배포하려면 데디 서버도 최신 소스로 패키징한다. RPC나 복제 데이터 형식은 추가하지 않았다.
- 새 DB 테이블/마이그레이션이나 데이터 초기화는 필요 없다. 이름 연결은 백엔드 메모리에만 저장한다.
- 이번 작업은 운영 백엔드/게임 서버/DB를 재시작하지 않았고, 배포본 교체나 업데이트 게시도 하지 않았다. 사용자가 수정한 맵/메시 에셋은 변경하지 않았다.
- 네이티브 회귀 검사에는 지연 성공/실패 응답 무시, 이전 HTTP 응답의 현재 pending 상태 보호, 맵 이동 설정 보존, 로그아웃 정리, 제한된 재시도, 이름 정리/대체 표기가 포함된다.
- 백엔드 검사는 이름 충돌, 다른 매치/비생존자 비공개, 현재 닉네임 사용, 이탈자 제외, 만료/재등록, 메모리 상한을 확인한다. 기존 업데이트 이어받기/롤백/설문 검사도 실행했다.
- 실제 EOS 통화와 실서버 3인 맵 이동은 별도로 확인해야 한다. 자동 검사는 마이크를 열지 않고 운영 DB에 접속하지 않는다.

최종 검증: Development Editor/Shipping 빌드 성공, .NET 관련 프로젝트 빌드 경고/오류 0개. 네이티브 35개 전부 성공(실패/미실행 0개, `Saved/VoiceLifecycleNative/index.json`), .NET FeatureChecks 35개와 별도 이어받기/파일 잠금 롤백 검사도 성공했다. 화면 렌더링 결과는 `Saved/VoiceParticipantTests`에 있다.

## 보이스 외 효과음 감쇄 추가 확인

`ProjectProject01SpatialAudio.cpp`의 공통 설정은 플레이어/파트너/마네킹 발소리의 합성음·음원 재생, 비명/신음 합성음, 쓰러지는 충격음에 연결되어 있다. 싱글/멀티에서 같은 재생 설정을 사용한다. 30m 이내 거리 게인 1, 30~60m 선형 감쇄(45m 게인 0.5, 60m 이상 0), 실제 표면이 Visibility 트레이스를 막으면 차폐 게인 0.25·LPF 600Hz·보간 0.15초다. 복잡 표면 충돌을 사용하고 발소리 발생점을 바닥 표면보다 약간 위에 둔다. 심장 박동/마네킹 포획 확인음 등 비공간 피드백은 의도적으로 이 정책에서 제외한다.

관련 설정값 평가와 차폐 충돌 자동 검사는 통과했다. 이것은 보이스 플러그인의 비어 있는 위치 함수와 다른 엔진 오디오 경로다. 다만 실제 사용자 맵의 모든 음원·벽/문 충돌 조합을 청취 검증한 것은 아니므로 ‘보이스를 제외한 모든 소리가 무조건 정상’이라고 단정하지 않는다.

## 전체 점검에서 추가로 발견한 항목 — 이번에는 수정하지 않음

점검은 보이스·인증/로비 요청·저장/불러오기·경기/맵 전환·업데이트 런처·크래시 수집·서버 세션 관리의 관련 경로를 중심으로 한 정적 검토와 기존 자동 회귀 검사다. 모든 소스와 모든 네트워크/장치/패키징 조합을 완전 검증했다는 뜻은 아니다.

### 우선 1: 실제 근접 보이스 감쇄 구현

클라이언트는 `ProjectProject01VoiceChatSubsystem.cpp`에서 `VoiceUser->Set3DPosition`을 호출하지만, 현재 점검한 UE 5.8 엔진의 `Engine/Plugins/Online/VoiceChat/EOSVoiceChat/Source/EOSVoiceChat/Private/EOSVoiceChatUser.cpp:652`는 해당 함수 본문이 `// Unimplemented`뿐이다. `JoinChannel`도 3D 속성을 실제 감쇄에 사용하지 않는다. 프로젝트 내 보이스 수신 코드에는 이를 대신할 거리별 수신 게인/공간 오디오 경로가 없다. 따라서 설정값을 전달하는 것만으로 목소리가 거리에 따라 작아진다고 말할 수 없다.

후속 보완은 서버가 검증한 생존자와 음성 참가자를 연결하고, 거리/청취 상태에 따른 수신 게인을 개인별 음량과 곱하거나 적절한 공간 오디오 경로로 수신 음성을 재생하는 것이다. 단순 음량 감쇄와 좌우 공간감은 별개이며, 두 PC 거리 이동 검사가 필요하다. 발소리/비명 등 기존 게임 SFX 감쇄와는 다른 경로다.

### 우선 2: 인증·로비의 오래된 HTTP 응답 무시

`ProjectProject01AuthSubsystem.cpp`의 `HandleRequestComplete` 및 `HandleServiceStatusRequestComplete`, `ProjectProject01LobbySubsystem.cpp`의 `HandleRequestComplete`는 현재 요청과 같으면 포인터를 비우지만, 다르다고 즉시 반환하지 않는다. `HandleSessionValidationComplete`와 `HandleGuideProgressRequestComplete`는 이미 이런 거부 검사가 있다. 취소·로그아웃·서버 IP 변경·새 요청 이후 늦게 전달된 콜백이 남아 있으면 이전 상태나 공지가 현재 UI를 덮을 여지가 있다. 실제 발생을 재현한 결과는 아니며, 요청 ID/세대 검사와 회귀 검사 추가를 권한다.

### 우선 3: EOS 음성 ID 본인 증명

`VoiceEndpoints.cs`는 게임 계정의 매치/생존자 자격과 ProductUserId 문자열 형식을 검사하지만, 요청자가 그 EOS ID를 실제 소유한다는 Connect ID 토큰 검증은 없다. 이번 중복 연결 차단은 이미 등록한 ID의 충돌을 막지만 최초 선점까지 소유 증명으로 바꾸지는 못한다. 공개 운영 전에는 EOS가 발급한 본인 증명을 검증한 후 계정과 연결하는 보완이 필요하다. 서버에서 확인한 닉네임이라는 것과 EOS ID의 본인 증명은 구별한다.

### 우선 4: 같은 학교/공유기에서의 보이스 토큰 요청 한도

`Program.cs`의 기존 `voice-token` 한도는 공인/접속 IP 기준 분당 30회다. 여러 사람이 같은 NAT를 사용하면 정상 플레이어들이 한도를 공유한다. 이번 이름 조회는 별도 `voice-roster` 한도를 사용하여 토큰 한도를 소모하지 않지만, 여러 경기의 동시 로그인 자체는 별도 개선 대상이다. 인증 계정별 한도와 IP 전체 보호 한도를 분리하고 학교 환경 동시 접속을 검사하는 편이 적절하다.

### 우선 5: 크래시 첨부 보관 정책과 덤프 취급

`CrashArtifactEndpoints.cs`는 파일별 64MiB 제한과 로그/XML 민감 문자열 제거가 있지만, `.dmp`는 바이너리 그대로 보관한다. 덤프 내부 메모리까지 비밀번호/토큰을 제거했다고 보장할 수 없다. 프로젝트 코드에서 첨부 파일의 전체 보관 용량/보관 기간에 따른 자동 정리 경로는 찾지 못했다. 덤프 선택 수집·관리자 접근·저장 공간 한도·보관 기간을 명확히 하는 것이 좋다. 보관 정책은 사용자 선택이 필요하며 이번 작업에서 자료를 삭제하지 않았다.
